# RichCode / Spectral for VS Code

A small MVP experiment that brings some ideas from **Spectral**, my old ADHD-friendly rich-text/code editor, into **Visual Studio Code**.

Spectral was originally a desktop text editor I wrote over 10 years ago during a between-jobs interlude. It was never a professionally designed UI/UX product, but it grew into a functionally rich productivity environment with hundreds of small features aimed at making code easier to navigate, annotate, generate, inspect, and maintain.

This repository contains an early VS Code extension experiment inspired by those ideas.

## What is Spectral?

Spectral is an attempt to make source code more than plain text, while still preserving the underlying plain text as the authoritative source.

The original idea was:

- plain text for the compiler
- rich text for the maintainer
- annotations, diagrams, colours, images, hyperlinks, generators, checkers, traces, and warnings for the human being trying to understand the code

The desktop version was designed around a line-to-line correspondence between the plain-text layer and the rich-text layer. This meant the code could remain normal code, while the surrounding rich layer could add meaning, context, intent, and evidence.

## Why an ADHD-friendly editor?

ADHD can make ordinary linear workflows unnecessarily punishing.

A task may not be hard because the underlying problem is hard. It may be hard because the workflow requires too much sustained attention, too much context-holding, too much remembering where things are, or too much switching between scattered artefacts.

Spectral was my attempt to compensate for this by taking the user through tasks via a more scenic route.

Some of the original desktop features included:

- trace analytics
- embedded generators
- embedded checkers
- data visualisers
- richer search and navigation
- rich annotations
- single-view multi-file editing
- code-aware productivity tools
- small automation helpers for repetitive attention-heavy tasks

The goal was to reduce the human attention cost of common maintenance tasks.

## Why this may matter in the age of AI-generated code

AI can now generate code faster than teams can absorb it.

That changes the bottleneck.

The scarce resource is no longer typing. It is:

- understanding
- reviewing
- trusting
- maintaining
- safely changing what has been produced

That is where Spectral-style editing may become useful even for neurotypical developers.

A codebase maintained by humans and AI needs more than comments. It needs visible intent, visible uncertainty, visible ownership, and visible evidence.

You may want to annotate code with things like:

- "What prompt produced this?"
- "Which parts were reviewed by a human?"
- "Which assumptions are still true?"
- "Why does this function exist?"
- "AI-generated, reviewed."
- "AI-generated, not yet trusted."
- "Business rule confirmed by Sarah."
- "Do not refactor unless you understand this production incident."
- "This terrifying regex was generated by a machine and only partly understood by mammals."

Software maintenance is often an exercise in recovering lost human intent.

AI makes that problem bigger.

Spectral is one attempt to make that intent visible again.

## About this VS Code extension

This extension is currently an MVP.

To get something working quickly, this version cuts several corners compared with the original desktop application. For example, it currently uses the VS Code **webview DOM** as the rich-text model, rather than a dedicated rich-text format and model.

That may change if the project continues to be of interest.

## Design principle

The guiding principle is:

> Keep the source code as source code, but let the editor carry richer human context around it.

In other words:

- the compiler should still see plain text
- the maintainer should see intent, structure, history, and warning labels
- AI-generated code should carry evidence of how it was produced, reviewed, and trusted

## Status

Experimental MVP.

This repository is not yet a polished product. It is a working exploration of an older idea that may have become more relevant in the age of AI-assisted programming.

## Possible future directions

Some possible next steps:

- replace the current webview-DOM-based rich-text model with a proper persistent model
- improve line-to-line synchronisation between source and rich annotations
- add better support for AI provenance annotations
- support richer embedded diagrams, generated artefacts, and review markers
- improve import/export of rich code documents
- explore integration with trace, test, coverage, and review data
- make the workflow smoother inside VS Code
